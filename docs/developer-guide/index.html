DOCS / 05 / DEVELOPER GUIDE

小而清晰，
可测试、可审计。

项目刻意保持轻量。贡献应优先落在现有职责模块，配套行为测试，并保留 CLI、打包、更新和跨平台边界。

开发环境

git clone https://github.com/Lijinzh/gpt-image-2-cli.git
cd gpt-image-2-cli
uv sync --frozen
uv run --frozen python -m gpt_image_cli --help

需要 Python 3.11+。依赖与命令统一通过锁定的 uv 环境运行，不要绕过 uv.lock 安装一套难以复现的开发依赖。

模块边界

模块职责
cli.py参数解析、命令编排、终端与 JSON 输出
config.py环境变量、URL 安全检查、CC-Switch 只读解析
proxy.py显式、环境与 Windows 系统代理选择
models.py请求参数验证和跨模块数据结构
client.pyHTTP 请求、超时、有限重连和图片下载
responses.pyJSON、SSE、Base64、URL 响应解析
image_io.py图片验证、画布修正和原子写入
updater.pyRelease 检查、完整性验证、延迟自更新
errors.py可安全显示的错误类型与稳定退出码
设计约束

不要把网络传输、文件写入或配置探测塞回 cli.py；也不要为单一需求引入服务层、依赖注入框架、插件系统或不必要的异步抽象。

实现一个改动

  1. 确认行为边界

    判断属于参数编排、配置、传输、解析、图片写入还是更新流程。

  2. 添加聚焦测试

    测试用户可见行为、退出码、JSON 字段和安全失败，而不是只覆盖内部实现。

  3. 完成最小实现

    保留现有命令、参数、环境变量和跨平台语义。

  4. 同步用户文档

    安装、配置、更新或 CLI 行为变化时更新 README 和本 Docs 站。

  5. 运行完整检查
    uv sync --frozen
uv run --frozen pytest
uv run --frozen ruff check .
uv build
uv run --frozen python -m gpt_image_cli --help

测试策略

  • CLI：参数冲突、JSON 稳定性、密钥脱敏和入口点。
  • 配置：环境变量优先级、CC-Switch 数据库异常、HTTP 边界。
  • 传输：区分连接建立失败与提交后失败，避免重复计费。
  • 响应：所有兼容结构、损坏 Base64、无效 JSON/SSE。
  • 图片：格式、尺寸、多图命名、覆盖保护和原子写入。
  • 更新：镜像一致性、manifest、wheel 元数据、助手脚本与 uv 环境识别。
  • 网站：本地链接、资源、六个栏目、导航和关键公开内容。

影响 CLI、打包、更新器或 Release 时，应运行完整测试、Ruff 与构建，而不是只跑单个测试文件。

安全开发规则

  • 测试和文档只使用明显假凭据。
  • 不要读取、提交或输出真实 API Key、Token、Cookie、Authorization Header、CC-Switch 数据库或用户生成图片。
  • 错误、对象 repr、代理显示与响应形状描述必须保持脱敏。
  • 远程 API 和更新资产继续要求 HTTPS 与固定来源，不增加跳过摘要校验的参数。
  • --json 只能输出可解析 JSON，不能混入提示、心跳或自动更新消息。

维护文档网站

GitHub Pages 发布根目录是 docs/。项目首页使用 styles.css 与 script.js；六个文档栏目共享 docs-page.css 与 docs-page.js。页面保持纯静态、无构建步骤，并让所有本地链接在 Pages 子路径下可解析。

uv run --frozen pytest tests/test_site.py

涉及可见布局还应在桌面端与 390×844 移动视口中打开本地站点，检查控制台、导航、横向溢出和复制交互。

版本与发布

  1. 同步版本

    pyproject.toml 与 src/gpt_image_cli/__init__.py 必须一致，并同步 uv.lock。

  2. 构建并生成清单
    uv build
$wheel = Get-ChildItem ./dist/*.whl | Select-Object -First 1
uv run --no-project python ./scripts/build_release_manifest.py $wheel.FullName
  3. 创建匹配标签

    版本 X.Y.Z 使用标签 vX.Y.Z。

  4. 验证公开资产

    检查完整 CI 矩阵、GitHub Release wheel、latest.json、大小与 SHA-256；配置凭据时再验证 Gitee/GitCode 完全一致。

本地构建不等于发布成功

只有匿名可下载的公开 Release 资产和完整 CI 结果都通过后，才能声明版本已经发布。

提交贡献

保留无关工作区改动，使用 codex/<description> 或聚焦功能分支；明确暂存属于当前任务的文件，不使用强制推送。提交信息简短描述实际结果。

更多仓库要求见 CONTRIBUTING.md、AGENTS.md 与 SECURITY.md。
